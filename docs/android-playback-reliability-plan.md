# Android 直播播放与闪退后续优化方案

基线为 GitHub `master` 的 `2d950f14a6b7005629e1f878ab5ee384bd96a44f`（Simple Live 1.12.30）。本次补丁修复了仍在播放时被非终止性报错触发重开、前后台命令与开关流交错、画中画重复挂载同一个全局键、退出播放器后残留定时退出任务四条路径。画中画故障在 Flutter 组件测试中复现，Android 原始进程退出仍需设备证据。 [GitHub 基线](https://github.com/Forlooong/dart_simple_live/commit/2d950f14a6b7005629e1f878ab5ee384bd96a44f) · [Flutter 全局键约束](https://api.flutter.dev/flutter/widgets/GlobalKey-class.html)

使用项目 CI 锁定的 Flutter 3.38.10 和 Dart 3.10.9 完成静态检查，55 项 Flutter 回归通过。回归使用直播平台及原生播放器替身，跳过用例未调用的 Windows 原生构建钩子。通过 Scoop 配置 Android SDK 36、NDK r28c 和 Rust 1.90，并成功交叉编译 Android ARM64 弹幕库。ADB 已在 Samsung 真机验证 GitHub 同提交正式包的冷启动，现有系统记录仅标记了强制停止。第三方报告的现场无法重现，本次结论以源码、自动化回归和已采集日志为限。修复版 APK 构建已随工作范围调整停止。

2026 年 11 月 21 日 15:19–15:31（北京时间），ADB 对该机正式版的斗鱼前台会话进行了 12 分钟观察。用户确认这段播放正常。该进程全程存活，采集的日志中未出现播放失败、自动恢复或崩溃信号。观察中抽样的播放区域有变化，两次总 PSS 约为 402 MiB 和 357 MiB。这段会话作为正常播放基线。

## P0 归因与真机验收

1. **保留进程退出原因。** 每次复现记录设备时间、版本与构建号、平台、操作和故障前后的 PID。用 `adb shell dumpsys activity exit-info com.xycz.simple_live` 和 `adb logcat -b crash -d -v threadtime` 查系统原因。PID 不变时查看 Flutter 和播放器日志，区分页面异常与流停止。PID 改变时按退出原因采集 Java 栈、Native tombstone、ANR trace 或内存数据。为每种退出原因保留独立归因，明确标记主动退出和用户强停。 [Android ApplicationExitInfo](https://developer.android.com/reference/android/app/ApplicationExitInfo)
2. **对照正式版与修复构建。** 在 Samsung SM-G9860（Android 13、arm64）和至少一台不同芯片的 Android 设备跑同一组操作。每个平台前台连续播放至少 30 分钟，覆盖 FLV/HLS（以平台实际提供为准）。单独执行断网 5 秒后恢复、Wi‑Fi 和移动网络互切、连续换房/切线路/返回 20 次、横竖屏和画中画进出 20 次、锁屏及前后台往返。默认硬解与关闭硬解各跑一轮，后台自动暂停开关各跑一轮。固定记录首次出帧耗时、转圈持续时间、自动恢复耗时、播放次数和任何进程退出。
3. **设置放行门槛。** 两个构建使用同一房间和设备设置。修复版在无主动退出的压力场景中应保持进程存活，单次故障只启动一条恢复链路，网络恢复后拿到可用源即继续出帧。确认离开播放器会取消重试和定时退出。每项声称改善的故障都关联到复现步骤和验证结果。 [现有发布门槛](release-gates.md)

## P1 有依据的候选改动

| 风险与依据 | 修改方向 | 验收 |
| --- | --- | --- |
| **静默卡流。** 缓冲事件用于显示和诊断。时钟停住且始终没有 error 或 EOF 时，当前恢复入口不会触发。 | 先采集缓冲时长与最后推进，再按直播、确认正在播放、前台且非暂停、持续无推进、无恢复正在进行等条件触发一次有上限的重新取源。以真机数据确定阈值。 | 模拟保持缓冲、缓冲标志滞后但时钟仍推进、后台暂停、弱网自然恢复和长时间停滞。只有最后一种路径发起恢复。 |
| **刷新失败令续播失去恢复能力。** 手动刷新先作废播放状态。拉取房间或线路失败时，原生可能继续播旧流，但界面和恢复所用的线路已被清空。 | 提交新房间和媒体选择前保留上一个有效会话。确认下播后才停流，确认切房后隔离旧结果。 | 在播放时让刷新网络请求超时，旧流继续推进且断开时仍可恢复。增加切房期间的旧请求回归。 |
| **恢复耗时与线路变化。** 恢复每次重新取房间、清晰度和签名地址，单次请求上下文默认 30 秒。新的线路列表可重排，当前按索引重试。 | 记录每阶段耗时和失败类别。为同一次用户意图设置总时限，区分暂时断网、限流、凭据失效与源耗尽。平台提供稳定线路标识时优先用它匹配替代源。 | 以到期地址、源列表重排、延迟响应和网络恢复验证重试上限、线路选择与可操作提示。 |
| **旧流事件与下一次打开之间没有原生标识。** 应用代次能隔离异步请求，原生 error/EOF 回调没有媒体 ID。 | 记录 open、stop、dispose 和最后收到的回调时间。根据结果增加原生会话关联或等待上一个终止事件完成，保留同一代次的真实启动失败。 | 让旧流在换线路后迟到发出 EOF 或 error，同时让新流继续推进。新流不被重开。 |
| **原生打开或释放可能长期等待。** 命令串行保护资源，卡住时导航会等待清理。 | 先记录视频初始化、open、dispose 和应用清理的分段耗时。若证据指向原生阻塞，从插件提供的停止或释放契约修复，并把阻塞阶段显示在诊断。 | 分别模拟卡 open 与卡 dispose。用户可以退出等待，后续不会在旧播放器仍持有资源时创建竞争播放器。 |

源码入口为 [直播间控制器](../simple_live_app/lib/modules/live_room/live_room_controller.dart)、[播放器控制器](../simple_live_app/lib/modules/live_room/player/player_controller.dart) 与 [播放请求上下文](../simple_live_core/lib/src/common/request_context.dart)。

## P2 平台与资源验证

- **画中画与渲染组件。** 当前 `floating` 6.0.0 仍用 10 ms 的周期探测状态。异步平台调用耗时超过间隔时，轮询可能重叠。平台通道报错也可能产生未捕获的异步异常。测量离开直播间后的调用频率，再改用 Android 画中画状态回调，或让探测跟随订阅启停并合并同时发起的请求。验收时覆盖进出画中画、通道异常和离开直播间，检查播放器实例唯一且探测正确停止。
- **解码器与设备资源。** 对 H.264/HEVC、默认硬解、软件解码和兼容输出分别记录原生崩溃栈、MediaCodec 错误和进程内存。长播和换房同时比较禁用弹幕及后台通知前后的内存曲线。由栈、退出原因和对照实验决定调整播放器、弹幕或后台任务的优先级。 [弹幕资源边界](danmaku-performance.md)
- **可导出的诊断。** 目前诊断附件只有分级计数。复用有界播放事件加入相对时间、阶段耗时、缓冲、重试、客户端主动退出类别和系统退出原因。仅持久化固定标签与数值，再对导出做敏感值回归。验收时用单份导出还原故障顺序，并检查没有房间号、签名 URL、请求头或账号数据。 [播放诊断实现](../simple_live_core/lib/src/common/playback_diagnostics.dart)
- **Android TV。** TV 控制器有对应的即时错误恢复和组件级前后台操作。用 TV 实际遥控场景复现并验证后迁移对应修复，包括返回焦点、连续换台和重进房间。 [TV 播放路径](../simple_live_tv_app/lib/modules/live_room/live_room_controller.dart)
