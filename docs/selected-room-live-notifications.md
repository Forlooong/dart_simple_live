# 指定关注直播间开播提醒

更新日期：2026-10-13。

本地验证：播放器、弹幕、关注导入、通知状态机、插件通信与点击路由共 68 项回归通过。插件通信测试隔离了原生端点，不能替代下文的 Android 真机验收。

本功能采用 **Android 系统后台周期检查 + 本地通知**。用户已选择不部署服务器、不依赖 Google Play 服务，并接受系统省电造成的延迟。只有主动开启铃铛的关注房间参与通知检查，其他关注房间不会自动订阅。

## 使用方法

1. 在 Android 应用的「关注用户」页面，点击所需直播间旁的铃铛。新关注房间默认关闭提醒。
2. 按提示允许应用发送通知。Android 13 及以上需要运行时通知许可；系统关闭应用通知或通知渠道时，即使后台检查成功，也可能看不到提醒。
3. 后台首次成功查到该房间状态时只建立基线，不补发已经开播的提醒。之后成功检查到「未开播 → 直播中」才发通知。
4. 点击开播通知进入对应直播间。关闭铃铛或取消关注会取消该房间订阅；没有已选房间时取消后台检查任务。
5. 关注页右上角的「开播提醒说明」可查看限制，并通过「通知设置」进入应用的系统设置。三星设备还需自行检查该应用是否被列入「深度休眠应用」。

关注列表的手动刷新和原有自动刷新设置只更新页面状态，不能代替系统后台检查，也不会额外发送开播提醒。关闭后重新开启同一房间的铃铛会重新建立基线。

## 提醒时间与使用边界

任务申请每 15 分钟检查一次。**15 分钟是系统允许的最短重复间隔，不是最长通知延迟，也不是准点执行承诺。** 锁屏、Doze、省电模式、设备负载、网络条件及厂商后台限制都可能使检查推迟；房间较多或接口较慢时，本轮也可能只检查部分房间。[Android 周期任务说明](https://developer.android.com/develop/background-work/background-tasks/persistent/getting-started/define-work)

| 场景 | 实际行为与限制 |
| --- | --- |
| 前台、退到后台、锁屏 | 由系统调度同一个周期任务。允许后台运行不代表每 15 分钟必定执行。 |
| 从最近任务列表划掉 | 与系统「强行停止」不同。是否继续执行仍受手机系统和厂商策略影响，需在目标三星设备验证。 |
| 系统设置中「强行停止」 | 后台任务不能绕过停止状态；需要手动重新打开应用，恢复任务注册。 |
| 设备重启 | 使用 WorkManager 的持久调度能力恢复任务，但不保证开机后立即检查，仍需实机验证。 |
| 新开铃铛时已在直播 | 首次成功检查只建基线，不补发；需后续观察到下播再开播才提醒。 |
| 两次检查之间完整地开播又下播 | 可能完全错过该场直播。 |
| 两次检查都显示直播中，但中间下播又重播 | 当前按状态转换识别，可能无法识别这次重播；未建立跨平台场次 ID 检测。 |
| 网络异常、接口拒绝、无效响应、超时 | 本轮该房间状态视为未知，保留前次成功状态；继续检查其他房间。 |
| 长时间没有执行检查 | 恢复后的状态差异可能触发延迟提醒；该提醒不能证明主播刚刚开播。 |

应用停止状态由 Android 控制，不能通过本功能保证划掉后即时通知或强行停止后继续工作。[Android 停止状态](https://developer.android.com/about/versions/15/behavior-changes-all#stopped-state)

## 状态、取消与去重规则

- 每个房间订阅带独立的 `generation`。关闭再开启、移除再订阅后，旧任务结果不能沿用为新订阅的基线。
- 仅首次成功读取建立基线；状态连续为直播中时不重复通知。接口异常不会被写成「未开播」，避免网络恢复造成假开播提醒。
- 后台在查询前、查询后及发送前重新检查当前订阅及其 generation。发送过程中同时关闭铃铛的情况，发送完成后再次核对并取消已展示通知；系统可能仍有非常短暂的展示窗口。
- 通知状态先写入持久文件，再调用 Android 显示通知。这偏向「同一状态转换最多尝试提醒一次」，避免进程重建后重放整批提醒。
- 写入状态后、显示通知前如果进程被系统结束，或者通知显示失败，可能漏掉这一条提醒；当前不为它补发。这里没有跨文件存储和 Android 通知服务的原子事务，不能声称必达或恰好一次送达。

## 本地存储与后台实现

| 组件 | 职责 |
| --- | --- |
| `FollowUser.notifyLive` | Hive 新字段 7，保存单个关注房间的选择；旧记录缺字段时默认关闭。 |
| `NotificationSubscription` / `NotificationConfig` | 后台需要的房间 ID、平台、主播名、generation 和对应平台账号配置快照。 |
| `FileNotificationStore` | UI 单独写 `subscriptions.json`，后台单独写 `state.json`；通过临时文件写入并重命名，避免读取半截 JSON。 |
| `LiveCheckRunner` | 使用真实平台状态查询、每房间超时、整轮时间预算和轮换起点，持久化基线、判断转换并发送通知。 |
| WorkManager | Android 上注册唯一周期任务，要求网络可用；使用 `ExistingPeriodicWorkPolicy.keep` 保持现有调度。 |
| `flutter_local_notifications` | 创建通知渠道、申请权限、即时展示通知和处理点击。 |
| `LiveStatusParser` | 校验四个平台实际使用的状态字段，缺失或错误类型抛异常，保留合法整数状态的原有含义。 |

后台通过独立 Flutter engine/isolate 执行，只初始化状态查询和通知需要的依赖，不打开播放器，也不复用主界面的 GetX 服务。B 站、斗鱼、虎牙的状态路径主要使用 HTTP/HTML；抖音路径还使用项目已有的 `dart_quickjs` 原生 FFI 签名及网页回退。

**只有唯一周期 worker 写状态文件。** UI 只写订阅快照，不写通知基线；不添加并行 one-off 检查，也不让关注页刷新写后台去重状态。后台不打开主界面持有的 Hive 2.2.3 盒子，避免跨 isolate 的缓存和写入一致性问题。

这一约束不能用普通 `RandomAccessFile.lock` 替代：Linux 文件建议锁属于进程，同进程多个 isolate 可以同时取得锁。将来如增加「立即检查并通知」或多个 worker，需要先引入支持事务的共享状态存储或可靠的跨 isolate 串行机制。[Dart 文件锁说明](https://api.dart.dev/dart-io/RandomAccessFile/lock.html)

### 账号信息与同步

供后台使用的 Cookie 副本仅保存在应用私有目录的订阅快照中；本功能没有额外监测服务器、推送 token 或云端订阅 API，不上传快照，也不新增 Cookie 日志。访问对应直播平台时，仍按现有站点逻辑携带该平台 Cookie。应用私有目录不是额外加密存储，不能描述为已经实现密钥保险库。

普通关注 JSON 导出保存 `notifyLive` 选择，不携带后台快照、generation 或通知状态账本。旧版 JSON 缺少该字段时，同一已有房间保留本机选择，新导入房间默认关闭；新版数据有明确字段时按字段导入。WebDAV、远程房间及其他覆盖同步需要在清空旧记录前保存原有选择，再重建订阅快照。抖音房间 ID 迁移要保留提醒选择，但新订阅重新建立基线。

## Android 与依赖配置

当前使用固定版本：

| 项目 | 版本或配置 |
| --- | --- |
| `workmanager` | `0.9.0+3` |
| `workmanager_android` | `0.9.0+2` |
| `workmanager_platform_interface` | `0.9.1+1` |
| `workmanager_apple` | `0.9.1+2` |
| `flutter_local_notifications` | `19.5.0` |
| Core library desugaring | `com.android.tools:desugar_jdk_libs:2.1.4` |
| Android 通知权限 | `POST_NOTIFICATIONS`，Android 13+ 在用户开启提醒时请求。 |
| 通知资源 | 专用 small icon，并配置资源保留，避免 release 资源裁剪移除。 |

本实现调用即时 `show()`，不使用精确闹钟，也不常驻前台服务。固定插件版本并提交真实解析生成的 `pubspec.lock`，避免后台插件的传递依赖漂移。版本配置依据 [Workmanager API](https://pub.dev/documentation/workmanager/0.9.0+3/workmanager/Workmanager-class.html) 与 [通知插件 19.5.0 配置](https://pub.dev/packages/flutter_local_notifications/versions/19.5.0)。

维护 Workmanager 依赖时必须成组核对 Dart、Android 和 Apple 的 Pigeon 消息编码，不能仅按版本约束允许就单独升级传递依赖。例如 interface `0.9.4` 新增消息类型，改变了 `InitializeRequest` 等类型的编码标记；配合 Android `0.9.0+2` 会在运行时错误解码，Dart 静态分析和普通单元测试不能发现。本表中的 interface/Android/Apple 三个版本已核对编码一致；升级后仍需验证原生初始化与真实后台执行。

## 验证与验收清单

本节是验收清单，**不是测试通过记录**。静态分析、单元测试和 APK 构建结果应以本次提交对应的实际执行输出为准；不能由构建成功推断真机后台送达成功。

自动化检查应覆盖：

- 首次直播/下播基线、下播转开播、持续直播不重复、超时及无效响应保持旧状态。
- 关闭再开启时 generation 变化、查询期间取消、通知显示期间取消、取消关注及最后一个订阅移除。
- 状态持久化后进程重建不重放、写入失败不发送、发送失败按当前最多一次尝试策略处理。
- 旧 Hive 数据、旧/新 JSON 导入导出、覆盖同步和抖音房间 ID 迁移保留正确选择。
- 大列表轮换及单房间故障不会长期阻塞其他房间。
